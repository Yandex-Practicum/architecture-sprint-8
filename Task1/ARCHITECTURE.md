# Архитектура управления учётными данными BionicPRO (Task1)

## Цели и ограничения

- **Унификация доступа** в BionicPRO через единый источник учётных записей во внешней системе (страна представительства компании).
- **Локальное хранение** персональных и медицинских данных не нарушается: они остаются в региональных/локальных хранилищах BionicPRO.
- **Безопасная работа с токенами**: фронтенд не получает access/refresh токены от IdP; используется схема с собственными сессионными токенами.
- **Поддержка нескольких внешних IdP** в разных странах (федерация удостоверяющих служб).

---

## Ключевые компоненты

### 1. Внешний источник учётных записей (страна представительства)

- **Роль**: единый каталог учётных записей для доступа в BionicPRO (идентификаторы, роли, минимальный профиль для SSO).
- **Размещение**: в стране представительства компании.
- **Хранит**: только данные, необходимые для авторизации и унификации доступа (account ID, роли, привязка к внешним IdP), **без** персональных и медицинских данных.
- **Интеграция**: запросы от Auth Gateway (BionicPRO) по защищённому каналу (например, OAuth2 client credentials или mTLS + API).

### 2. Auth Gateway (шлюз аутентификации) — внутри BionicPRO

- **Роль**: единственная точка входа для аутентификации; фронтенд с ней общается, с IdP — нет.
- **Функции**:
  - Определение нужного внешнего IdP (по стране/тенанту/параметру).
  - Редирект пользователя на выбранный IdP (OAuth2/OpenID Connect Authorization Code).
  - Приём callback с **authorization code** от IdP; обмен code на access/refresh токены **только на бэкенде** (фронтенд кода и токенам IdP не имеет доступа).
  - Запрос данных учётной записи во **внешнем источнике учётных записей** (по sub/email из IdP) для унификации.
  - Выдача фронтенду **собственных** сессионных артефактов:
    - **HttpOnly, Secure cookie** с сессионным идентификатором и/или
    - **Opaque session token** или короткоживущий **JWT, подписанный BionicPRO** (не IdP), передаваемый только по безопасному каналу.
  - Refresh: на бэкенде по refresh-токену IdP (хранится только на сервере) продление сессии и при необходимости — новая пара cookie/opaque token для клиента.

Таким образом **схема с токенами безопасна**: фронтенд не получает и не хранит access/refresh токены IdP.

### 3. Внешние удостоверяющие службы (IdP по странам)

- Несколько внешних IdP (по одному или несколько на страну/регион), с которыми Auth Gateway взаимодействует по OAuth2/OpenID Connect.
- Пользователь аутентифицируется в «своём» IdP; Auth Gateway после успешной аутентификации связывает сессию с учётной записью из внешнего источника.

### 4. Локальные данные BionicPRO

- API, БД, CRM и т.д. остаются локальными/региональными.
- Персональные и медицинские данные хранятся только в этих компонентах; внешний источник учётных записей их не содержит и не обрабатывает.
- API проверяет запросы по сессионному токену/cookie через Auth Gateway (или через общий JWKS/подпись BionicPRO), не по токенам IdP.

## Потоки данных

1. **Вход пользователя**  
   Пользователь → Frontend → Auth Gateway → редирект на выбранный IdP → аутентификация в IdP → callback на Auth Gateway с code → обмен code на токены IdP на бэкенде → запрос учётной записи во внешнем источнике → создание сессии → установка cookie/выдача opaque token фронтенду.

2. **Запросы к API**  
   Frontend отправляет cookie или opaque token (в заголовке). API проверяет сессию через Auth Gateway (или локально по подписи JWT BionicPRO); доступ к персональным/медицинским данным — из локальных БД.

3. **Обновление сессии**  
   При истечении сессии фронтенд обращается к Auth Gateway (например, `/refresh` с cookie). Auth Gateway по сохранённому refresh-токену IdP получает новые токены IdP на бэкенде и выдаёт новую сессию фронтенду; токены IdP по-прежнему не передаются на фронтенд.

## C4 и размещение на диаграмме

- **Уровень контекста (C4 Context)**  
  - Люди: Покупатель протеза, Пилот протеза, Оператор производства, ML-инженер.  
  - Внешние системы: «Внешний источник учётных записей» (страна представительства), «Внешние IdP» (несколько удостоверяющих служб по странам).  
  - Система: BionicPRO.

- **Уровень контейнеров (C4 Container)**  
  Внутри BionicPRO добавляются:  
  - **Auth Gateway** — шлюз аутентификации (обмен кода на токены IdP на бэкенде, запрос учётных данных во внешнем источнике, выдача собственных сессионных токенов).  
  - Остальные контейнеры (Интернет-магазин, CRM, API, CLI и т.д.) получают доступ «через» сессию, выданную Auth Gateway; API проверяет сессию у Auth Gateway или по подписи BionicPRO.

На диаграмме в draw.io отражены: BionicPRO, Auth Gateway, внешний источник учётных записей, несколько внешних IdP, фронтенд-приложения, API и хранилища данных; потоки — без передачи токенов IdP на фронтенд.

## Резюме соответствия требованиям

| Требование | Реализация |
|------------|------------|
| Унификация доступа через внешний источник в стране представительства | Внешний источник учётных записей; Auth Gateway запрашивает учётные данные только из него. |
| Локальное хранение персональных и медицинских данных | Персональные/медицинские данные только в API и БД BionicPRO; внешний источник — только учётные данные для доступа. |
| Безопасная схема: фронтенд не получает токены IdP | Auth Gateway обменивает code на токены IdP на бэкенде; фронтенду выдаются только cookie/opaque token или JWT BionicPRO. |
| Поддержка нескольких внешних IdP по странам | Auth Gateway выбирает IdP (страна/тенант) и выполняет OAuth2/OIDC flow с выбранным IdP. |
