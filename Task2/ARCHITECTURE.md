# Архитектура сервиса отчётов BionicPRO (Task2)

## Цели

- Дать пользователям возможность получать данные о работе своего протеза и просматривать их в виде отчёта.
- Реализовать отдельный сервис отчётов, который формирует отчёты из данных, собираемых из разных источников: **CRM** и **DB** (основная БД с телеметрией и данными приложения).

Решение включает **ETL-процесс** (Apache Airflow), объединяющий данные с датчиков и из CRM, формирование **витрины отчётности в OLAP БД** и выдачу **итогового отчёта по пользователю через бэкенд-сервис API** из исходной архитектуры BionicPRO.

---

## Источники данных

### 1. CRM и CRM DB

- **CRM** (Bitrix24) — заказы, клиенты, контракты, данные о протезах (модель, дата поставки, сервисные события).
- **CRM DB** (например, Oracle Database) — хранилище данных CRM; используется как источник для ETL (заказы, привязка устройства к пользователю, контактные и сервисные данные).

### 2. Основная БД (DB)

- **Database** (PostgreSQL) — операционная БД бэкенда API.
- Содержит данные, поступающие от **программы в чипе протеза** (телеметрия, события с датчиков) и от **приложения для донастройки протеза** (сессии использования, команды, метрики).
- Ключевые сущности для отчётов: пользователь/устройство, временные ряды телеметрии, события, агрегаты по сессиям.

Объединение по идентификатору пользователя/устройства позволяет строить отчёт «работа протеза» с учётом и телеметрии, и данных из CRM (например, дата выдачи, сервисные визиты).

---

## ETL-процесс (Apache Airflow)

### Назначение

- **Extract**: чтение данных из CRM DB и из основной БД (PostgreSQL).
- **Transform**: сопоставление по пользователю/устройству, очистка, агрегация (по дням/неделям, метрики использования, события), обогащение данными из CRM.
- **Load**: загрузка результата в **OLAP БД** (витрина отчётности).

Оркестрация заданий (расписание, зависимости, повтор при сбоях) выполняется **Apache Airflow**.

### Реализация в Airflow

- **DAG** с расписанием (например, ежедневно в нерабочее время).
- Задачи (Operators):
  - **Extract из CRM DB**: подключение к CRM DB (Oracle), выгрузка изменённых/новых записей по заказам, клиентам, привязке устройств к пользователям (инкрементальная выгрузка по дате изменения или по ID).
  - **Extract из DB (PostgreSQL)**: выгрузка телеметрии и событий за период, агрегатов по сессиям (или сырых данных для последующей агрегации в ETL).
  - **Transform**: объединение потоков по ключу (user_id / device_id), расчёт показателей (время использования, количество срабатываний, ошибки, калибровки и т.д.), обогащение атрибутами из CRM (модель протеза, дата выдачи).
  - **Load**: запись в OLAP БД (полная перезагрузка витрины за период или инкрементальное обновление).

Данные в витрине хранятся в виде, удобном для отчётов: срезы по пользователю, по периоду, по типу метрики (звезда/снежинка или денормализованные таблицы фактов и измерений).

---

## Витрина отчётности (OLAP БД)

- **Роль**: хранилище готовых данных для отчётов; оптимизировано для аналитических запросов (агрегации, срезы по времени и по пользователю).
- **Варианты реализации**: отдельная БД (например, PostgreSQL с партиционированием и индексами под аналитику) или специализированное OLAP-хранилище (например, ClickHouse, Greenplum, или звездообразная схема в том же PostgreSQL).
- **Содержимое витрины** (концептуально):
  - Измерения: пользователь, устройство, модель протеза, дата/период, регион (при необходимости).
  - Факты/метрики: время работы протеза, количество сессий, события с датчиков, ошибки, калибровки, сервисные события из CRM.
- Итоговый отчёт по пользователю формируется выборкой из витрины по `user_id` и опционально по периоду.

---

## Доступ к отчёту через API

- **Бэкенд-сервис API** (из исходной архитектуры BionicPRO — например, Spring Boot) выступает единственной точкой выдачи отчётов для клиентов.
- **Поток**:
  1. Пользователь (пилот протеза) или покупатель запрашивает отчёт через **фронтенд** (веб или приложение для донастройки протеза).
  2. Фронтенд обращается к **API** (например, `GET /api/reports/user/{userId}` или `GET /api/reports/me` с авторизацией).
  3. API проверяет права доступа (отчёт только по своему пользователю или по доверенным ролям), запрашивает данные из **OLAP БД** (витрины отчётности) и возвращает клиенту готовый отчёт (JSON или иной формат).
- API не дублирует логику ETL; он только читает уже подготовленную витрину. Актуальность отчёта определяется расписанием ETL в Airflow (например, отчёт за вчера — после ночного прогона DAG).

---

## Потоки данных (сводка)

1. **Наполнение витрины (ETL)**  
   CRM DB + Database (PostgreSQL) → Apache Airflow (Extract → Transform → Load) → OLAP БД (витрина отчётности).

2. **Получение отчёта пользователем**  
   Пользователь → Фронтенд → API → OLAP БД → ответ с отчётом.

3. **Исходные потоки (без изменений)**  
   Чип протеза и приложение донастройки по-прежнему отправляют телеметрию и данные в API, API сохраняет их в основную БД; ETL забирает эти данные из БД, а не из API в реальном времени.

## Размещение на диаграмме (draw.io)

- Внутри границы **BionicPRO** отображаются:
  - **CRM**, **CRM DB** — источники данных из исходной архитектуры.
  - **API**, **Database (PostgreSQL)** — бэкенд и основная БД из исходной архитектуры.
  - **Apache Airflow** — оркестратор ETL (контейнер/сервис).
  - **OLAP БД** — витрина отчётности (отдельное хранилище).
  - **Фронтенд** — запрос отчёта пользователем.
- Связи:
  - Airflow → Extract из CRM DB и из Database; Airflow → Load в OLAP БД.
  - Фронтенд → API «запрос отчёта»; API → OLAP БД «чтение витрины».

Таким образом, архитектура решения для подготовки и получения отчётов включает ETL на Apache Airflow, объединяющий данные с датчиков (из DB) и из CRM, витрину в OLAP БД и выдачу итогового отчёта по пользователю через бэкенд-сервис API.
