# Архитектурное решение для управления учётными данными пользователя в BionicPRO

## Обзор архитектурного решения

Предлагаемое решение обеспечивает унификацию доступа в системе BionicPRO через интеграцию с внешними удостоверяющими службами (IdP), при этом гарантируя безопасность работы с токенами и соблюдение требований по локальному хранению персональных и медицинских данных.

**Важный контекст:** Компания в настоящее время работает в России, но планирует расширение деятельности в другие страны. BionicPRO работает с медицинскими данными, которые подлежат особому правовому регулированию в различных юрисдикциях. Архитектура спроектирована с учётом необходимости соблюдения различных правовых требований и возможности адаптации к новым рынкам.

### Ключевые принципы решения:

1. **Унификация доступа** - через единую точку входа (Identity Broker)
2. **Безопасность токенов** - фронтенд не получает токены от внешних IdP
3. **Множественные IdP** - поддержка различных удостоверяющих служб в разных странах
4. **Локальное хранение** - персональные и медицинские данные хранятся локально в соответствии с требованиями страны пользователя
5. **Соблюдение правовых требований** - архитектура адаптируется к различным юрисдикциям и поддерживает международное расширение

---

## Архитектурные компоненты

### Identity Broker

**Тип:** Container (внутри системы BionicPRO)

**Назначение:**
Identity Broker является центральным компонентом системы аутентификации и авторизации. Он выполняет роль посредника между клиентскими приложениями и внешними удостоверяющими службами.

**Функциональность:**
- Получает токены от внешних Identity Providers (IdP) через протоколы OAuth 2.0 / OIDC
- Обменивает токены внешних IdP на собственные токены системы BionicPRO
- Исключает передачу токенов от внешних IdP фронтенд-приложениям
- Выдаёт собственные access- и refresh-токены клиентским приложениям
- Обеспечивает валидацию токенов для API-сервисов

**Технологии:**
- Keycloak (как основа для Identity Broker)
- Spring Boot (для кастомных расширений и интеграций)

**Взаимодействие:**
- Принимает запросы на аутентификацию от клиентских приложений
- Интегрируется с множественными внешними IdP (разные страны)
- Запрашивает данные учётных записей через User Account Service
- Предоставляет API для валидации токенов

---

### User Account Service

**Тип:** Container (внутри системы BionicPRO)

**Назначение:**
Сервис для унификации доступа к данным учётных записей пользователей из внешних источников.

**Функциональность:**
- Запрашивает данные учётных записей из внешнего источника, расположенного в стране представительства компании
- Синхронизирует полученные данные с локальной базой данных
- Обеспечивает единообразный доступ к учётным данным независимо от источника

**Технологии:**
- Spring Boot
- REST API

**Взаимодействие:**
- Получает запросы от Identity Broker на основе токенов от внешних IdP
- Обращается к внешнему источнику учётных данных для получения информации о пользователе
- Сохраняет и обновляет данные в локальной базе данных
- Обеспечивает соответствие принципам локального хранения персональных данных

---

### Внешние Identity Providers

**Тип:** Software System (вне системы BionicPRO)

**Назначение:**
Внешние удостоверяющие службы, действующие в различных странах, где представлена компания.

**Функциональность:**
- Аутентификация пользователей согласно требованиям конкретной страны
- Выдача токенов доступа (access tokens) и обновления (refresh tokens) через OAuth 2.0 / OIDC
- Поддержка различных стандартов и протоколов аутентификации, принятых в разных странах

**Особенности:**
- Каждая страна может иметь свою удостоверяющую службу
- Identity Broker поддерживает интеграцию с множественными IdP одновременно
- Выбор конкретного IdP зависит от страны пользователя или его предпочтений

**Протоколы:**
- OAuth 2.0
- OpenID Connect (OIDC)

---

### Внешний источник учётных данных

**Тип:** Software System (вне системы BionicPRO)

**Назначение:**
Внешний источник данных учётных записей пользователей, расположенный в стране представительства компании.

**Функциональность:**
- Хранение и предоставление данных учётных записей пользователей
- Обеспечение единого источника истины для учётных данных
- Интеграция с корпоративными системами управления пользователями

**Взаимодействие:**
- User Account Service запрашивает данные учётных записей из этого источника
- Данные используются для синхронизации с локальной базой данных BionicPRO
- Обеспечивает унификацию доступа к учётным данным

**Функциональность:**

- Поддержка распределённого хранения данных по странам для соблюдения местного законодательства
- Хранение авторизационных данных (токены, сессии) в соответствии с требованиями страны пользователя

**Функциональность:**
- Валидация токенов через Identity Broker
- Обработка бизнес-логики приложения
- Доступ к локально хранимым персональным и медицинским данным

### Приложение для донастройки протеза

**Изменение роли:**
Приложение теперь получает токены от Identity Broker, а не напрямую от внешних IdP.

**Функциональность:**
- Получение токенов от Identity Broker для доступа к API
- Использование собственных токенов системы BionicPRO (не токенов внешних IdP)
- Аутентификация пользователей через единую точку входа (Identity Broker)

## Поток аутентификации и авторизации

### Процесс аутентификации:

1. **Инициация аутентификации**
   - Пользователь открывает приложение для донастройки протеза
   - Приложение перенаправляет пользователя на Identity Broker

2. **Выбор Identity Provider**
   - Identity Broker определяет или предлагает пользователю выбрать внешний IdP в зависимости от страны
   - Пользователь перенаправляется на выбранный внешний IdP

3. **Аутентификация во внешнем IdP**
   - Пользователь проходит аутентификацию во внешнем IdP
   - Внешний IdP возвращает токены (access token и refresh token) в Identity Broker

4. **Получение данных учётной записи**
   - Identity Broker использует полученные токены для запроса данных учётной записи через User Account Service
   - User Account Service обращается к внешнему источнику учётных данных
   - Полученные данные синхронизируются с локальной базой данных

5. **Выдача токенов системы**
   - Identity Broker обменивает токены внешнего IdP на собственные токены системы BionicPRO
   - Собственные токены выдаются приложению (токены внешнего IdP не передаются фронтенду)

6. **Использование API**
   - Приложение использует токены от Identity Broker для доступа к API
   - API валидирует токены через Identity Broker
   - API получает доступ к локально хранимым персональным и медицинским данным

## Архитектурные принципы

### Безопасность токенов

**Принцип:** Токены от внешних IdP никогда не передаются фронтенд-приложениям.

**Реализация:**
- Identity Broker получает токены от внешних IdP на стороне сервера
- Identity Broker обменивает их на собственные токены системы
- Фронтенд получает только токены, выданные Identity Broker
- Это исключает утечку токенов внешних IdP и обеспечивает дополнительный уровень безопасности

### Унификация доступа

**Принцип:** Единая точка входа для всех клиентских приложений независимо от используемого внешнего IdP.

**Реализация:**
- Все клиентские приложения взаимодействуют только с Identity Broker
- Identity Broker абстрагирует детали работы с различными внешними IdP
- Клиентские приложения не знают, какой именно внешний IdP используется

### Поддержка множественных IdP

**Принцип:** Система должна поддерживать различные удостоверяющие службы, действующие в разных странах.

**Реализация:**
- Identity Broker может быть настроен для работы с несколькими внешними IdP одновременно
- Выбор IdP может быть автоматическим (на основе геолокации) или ручным (выбор пользователя)
- Архитектура позволяет легко добавлять новые внешние IdP без изменения клиентских приложений

### Локальное хранение данных

**Принцип:** Персональные и медицинские данные пользователей должны храниться локально в соответствии с требованиями правового регулирования страны пользователя.

**Реализация:**
- База данных BionicPRO хранит персональные и медицинские данные локально
- "Локально" означает хранение данных в стране пользователя или в соответствии с требованиями конкретной юрисдикции
- Архитектура поддерживает возможность распределённого хранения данных по странам для соблюдения местного законодательства
- Внешний источник учётных данных используется только для получения базовой информации об учётной записи
- User Account Service синхронизирует учётные данные, но не персональные/медицинские данные
- Медицинские данные никогда не передаются во внешние системы
- Авторизационные данные (токены, сессии) также хранятся в соответствии с требованиями страны пользователя

## Соответствие требованиям

### Унификация доступа

Система обеспечивает унификацию доступа через:
- Единую точку входа (Identity Broker)
- Запрос данных учётных записей из внешнего источника через User Account Service
- Единообразный интерфейс для всех клиентских приложений

### Безопасная схема работы с токенами

Система исключает передачу токенов внешних IdP фронтенду:
- Identity Broker получает токены от IdP на стороне сервера
- Identity Broker обменивает их на собственные токены системы
- Фронтенд получает только токены, выданные Identity Broker
- Access- и refresh-токены от IdP остаются на сервере

### Поддержка множественных внешних IdP

Система поддерживает различные удостоверяющие службы:
- Identity Broker может быть настроен для работы с несколькими внешними IdP
- Каждый IdP может действовать в своей стране
- Выбор IdP может быть автоматическим или ручным
- Архитектура позволяет легко добавлять новые IdP

### Локальное хранение данных

Принципы локального хранения не нарушены:
- Персональные данные хранятся локально в базе данных BionicPRO в соответствии с требованиями страны пользователя
- Медицинские данные хранятся локально в базе данных BionicPRO с соблюдением требований медицинского законодательства
- Архитектура поддерживает распределённое хранение данных по странам для соблюдения местного законодательства
- Внешний источник используется только для учётных данных (не персональных/медицинских)
- User Account Service синхронизирует только учётные данные
- Авторизационные данные хранятся в соответствии с требованиями страны пользователя
- Система может быть адаптирована к требованиям различных юрисдикций при выходе на новые рынки

## Соблюдение правовых требований разных стран

### Принципы соблюдения правовых требований

**Гибкость архитектуры:**
- Архитектура спроектирована с учётом необходимости адаптации к различным правовым требованиям
- Компоненты системы могут быть настроены для работы в соответствии с требованиями конкретной страны
- Поддержка различных режимов хранения данных в зависимости от юрисдикции

**Локальное хранение данных:**
- "Локальное хранение" интерпретируется как хранение данных в стране пользователя или в соответствии с требованиями конкретной юрисдикции
- Медицинские данные хранятся в соответствии с требованиями медицинского законодательства страны пользователя
- Персональные данные хранятся с соблюдением требований законодательства страны пользователя
- Авторизационные данные (токены, сессии) также хранятся в соответствии с требованиями страны пользователя

**Изоляция данных по странам:**
- Архитектура поддерживает возможность изоляции данных по странам
- Данные пользователей из разных стран могут храниться в отдельных хранилищах или регионах
- Это обеспечивает соблюдение требований о запрете трансграничной передачи данных в некоторых юрисдикциях

**Адаптация к новым рынкам:**
- При выходе на новый рынок система может быть настроена для соблюдения местных требований
- Identity Broker может быть интегрирован с местными удостоверяющими службами
- User Account Service может быть адаптирован для работы с местными источниками учётных данных
- База данных может быть развёрнута в стране пользователя или в соответствии с местными требованиями

## Масштабируемость и расширяемость

### Добавление новых внешних IdP

Архитектура позволяет легко добавлять новые внешние IdP:
- Identity Broker поддерживает конфигурацию множественных IdP
- Добавление нового IdP не требует изменений в клиентских приложениях
- User Account Service может быть расширен для работы с дополнительными источниками данных
- При выходе на новый рынок может быть добавлен соответствующий IdP для этой страны

### Горизонтальное масштабирование

Компоненты системы могут масштабироваться независимо:
- Identity Broker может быть развёрнут в кластере
- User Account Service может масштабироваться горизонтально
- API может масштабироваться независимо от других компонентов

### Международное расширение

Архитектура поддерживает расширение на новые рынки:
- Компоненты могут быть развёрнуты в новых регионах/странах
- База данных может быть распределена по странам для соблюдения локальных требований
- Identity Broker может быть настроен для работы с местными IdP
- Система может быть адаптирована к новым правовым требованиям без изменения базовой архитектуры

## Безопасность

### Защита токенов

- Токены внешних IdP никогда не покидают серверную часть
- Identity Broker использует безопасные механизмы хранения токенов
- Собственные токены системы имеют ограниченное время жизни
- Refresh-токены используются для обновления access-токенов

### Защита данных

- Персональные и медицинские данные хранятся локально в соответствии с требованиями страны пользователя
- Данные шифруются при передаче между компонентами
- Доступ к данным контролируется через систему авторизации
- Внешние системы не имеют прямого доступа к персональным/медицинским данным
- Авторизационные данные (токены, сессии) хранятся с соблюдением требований безопасности и правового регулирования
- Поддержка изоляции данных по странам для соблюдения требований о трансграничной передаче данных

---

## Заключение

Предложенное архитектурное решение обеспечивает:

1. **Унификацию доступа** через единую точку входа (Identity Broker) и единый источник учётных данных
2. **Безопасность** за счёт исключения передачи токенов внешних IdP фронтенду
3. **Гибкость** в поддержке различных удостоверяющих служб в разных странах
4. **Соответствие требованиям** по локальному хранению персональных и медицинских данных
5. **Соблюдение правовых требований** различных юрисдикций с возможностью адаптации к новым рынкам
6. **Готовность к международному расширению** с учётом различий в правовом регулировании разных стран
