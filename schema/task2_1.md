# C4-модель BionicPRO: Архитектура подготовки и получения отчётов

## C4: Уровень контекста (System Context)

### Люди (Person)

- **Покупатель протеза (Customer)** — человек, который выбирает и оплачивает бионический протез через
  интернет‑магазин.
- **Пилот протеза (Pilot)** — пользователь протеза, с мышц которого считываются миосигналы для управления протезом;
  использует мобильное приложение для донастройки и получения отчётов о работе протеза.
- **Оператор производства (Production Operator)** — сотрудник, который работает в CRM, просматривает и сопровождает
  заказы, управляет процессом производства протезов.
- **ML‑инженер (ML Engineer)** — специалист по машинному обучению, использующий консольный инструмент (cli‑tool) для
  работы с телеметрией и обучением ML‑моделей.
- **Администратор BionicPRO (System/Admin)** — администратор ИТ‑системы BionicPRO, настраивает интеграции с внешними
  удостоверяющими службами (IdP), управляет политиками доступа и безопасностью.

### Основные программные системы (Software System)

- **BionicPRO (core software system)** — внутренняя ИТ‑система компании, обеспечивающая изготовление, настройку,
  эксплуатацию и анализ данных бионических протезов, управление учётными записями пользователей, а также подготовку и
  предоставление отчётов по данным с датчиков и CRM.
- **Интернет‑магазин (Bitrix24 Web Shop)** — внешняя веб‑система, через которую покупатель выбирает протез, оформляет
  заказ и производит оплату; передаёт заказы в CRM.
- **CRM (Bitrix24 CRM)** — внешняя по отношению к BionicPRO система для ведения заказов, клиентов и производства;
  использует отдельную БД CRM DB (например, Oracle Database 12). Данные CRM являются одним из источников для
  ETL-процесса формирования витрины отчётности.
- **Внешние удостоверяющие службы (External IdP Systems)** — сторонние Identity Provider‑ы (Keycloak, национальные или
  корпоративные IdP в разных странах), которые аутентифицируют пользователей по протоколам OAuth2/OIDC.
- **Государственные/корпоративные каталоги по странам (Local External Account Sources)** — внешние источники учётных
  записей (каталоги/IdP), развёрнутые в каждой стране присутствия компании и подчиняющиеся локальному законодательству о
  персональных и медицинских данных.

### Отношения (Context Relationships)

- Покупатель протеза взаимодействует с Интернет‑магазином для выбора, заказа и оплаты протеза.
- Интернет‑магазин передаёт информацию о заказах в CRM, где с ними работает Оператор производства.
- Пилот протеза взаимодействует с Программой в чипе протеза (через свои миосигналы) и с Мобильным приложением
  донастройки (через интерфейс приложения).
- Пилот протеза аутентифицируется через Мобильное приложение и внешний IdP, при этом все операции проходят через
  Identity Gateway внутри BionicPRO.
- Пилот протеза запрашивает отчёт о работе своего протеза через Мобильное приложение → Core API, который читает готовую
  витрину отчётности из OLAP БД (ClickHouse).
- ML‑инженер использует cli‑tool, который взаимодействует с API BionicPRO и внутренней БД BionicPRO для работы с
  телеметрией и моделями.
- Apache Airflow (ETL-оркестратор) периодически извлекает данные из BionicPRO DB (данные с датчиков) и CRM DB (данные о
  клиентах и заказах), трансформирует и загружает их в OLAP БД (ClickHouse), формируя готовую витрину отчётности.
- Все внутренние компоненты BionicPRO используют Identity Gateway как единый слой аутентификации и авторизации;
  персональные и медицинские данные хранятся только в локальных сервисах профилей и БД внутри страны.

## C4: Уровень контейнеров (Container Diagram)

### BionicPRO — перечень контейнеров

Внутри программной системы **BionicPRO** выделяются следующие контейнеры:

#### 1. Программа в чипе протеза (Prosthesis Chip Program)

- **Тип:** Embedded Software System (ESP32).
- **Ответственность:**
    - считывание данных с миодатчиков пилота протеза;
    - распознавание движений по миосигналам и управление актуаторами;
    - обработка команд от мобильного приложения;
    - передача технической телеметрии и данных через встроенный 4G‑модуль во внутренние системы BionicPRO.

#### 2. Мобильное приложение для донастройки протеза (Tuning Mobile App)

- **Тип:** Container (iOS, Android).
- **Ответственность:**
    - управление протезом (отправка команд в чип);
    - донастройка алгоритмов распознавания движений;
    - инициирование передачи телеметрии и других данных через API BionicPRO;
    - предоставление пользователю (Пилоту) интерфейса для входа в систему и запроса/скачивания отчётов о работе
      протеза.
- **Взаимодействует с:**
    - Программой в чипе (двусторонний обмен командами и данными);
    - Identity Gateway (аутентификация/авторизация через внутренние токены BionicPRO);
    - Core API BionicPRO (бизнес‑операции, запрос и получение отчётов).

#### 3. Внутренний API BionicPRO (Core API)

- **Тип:** Container (например, SpringBoot + ElasticSearch и др.).
- **Ответственность:**
    - приём телеметрии и данных от чипа и мобильного приложения;
    - предоставление интерфейсов для записи и чтения данных из внутренней БД BionicPRO;
    - точка интеграции для cli‑tool и других внутренних сервисов;
    - **предоставление итоговых отчётов по пользователю** — API читает готовую витрину отчётности из OLAP БД (
      ClickHouse) и отдаёт отчёт мобильному приложению;
    - авторизация входящих запросов по внутренним токенам BionicPRO, проверяемым через Identity Gateway.
- **Взаимодействует с:**
    - BionicPRO DB (запись/чтение телеметрии и конфигураций);
    - OLAP БД ClickHouse (чтение готовой витрины отчётности для формирования отчётов пользователю);
    - User Profile Service (проверка связи user id ↔ протезы для ограничения доступа к отчётам);
    - Identity Gateway (валидация токенов).

#### 4. База данных BionicPRO (BionicPRO DB)

- **Тип:** Container (PostgreSQL).
- **Ответственность:**
    - хранение телеметрии протезов и миосигналов;
    - хранение конфигураций для донастройки протезов;
    - хранение технических и аналитических данных, необходимых отделу ML и разработке.
- **Роль в отчётности:** является одним из двух источников данных для ETL-процесса (данные с датчиков протезов).

#### 5. cli‑tool для ML (ML CLI Tool)

- **Тип:** Container (консольный инструмент, например SpringBoot, ElasticSearch и др.).
- **Ответственность:**
    - чтение и выгрузка телеметрии и миосигналов из БД BionicPRO;
    - подготовка данных и обучение ML‑моделей;
    - обновление конфигураций или версий моделей, используемых в Программе в чипе.

#### 6. Identity Gateway (Auth API)

- **Тип:** Container (например, SpringBoot).
- **Ответственность:**
    - интеграция с внешними IdP (Keycloak, национальные и корпоративные IdP в разных странах) по OAuth2/OIDC;
    - реализация унифицированного входа для всех клиентов (мобильное приложение, интернет‑магазин, CRM, внутренние
      инструменты);
    - приём auth‑code от фронтенда, обмен кода на access/refresh‑токены у внешнего IdP;
    - хранение и безопасное использование IdP‑токенов во внутреннем хранилище, без отдачи этих токенов на фронтенд;
    - выпуск внутренних access‑ и refresh‑токенов BionicPRO (прокси‑токены);
    - валидация внутренних токенов для Core API и других контейнеров;
    - аудит и логирование операций аутентификации и выдачи токенов.

#### 7. Encrypted Token Store (Secure Token Storage)

- **Тип:** Container (может быть отдельным сервисом или компонентом внутри Identity Gateway).
- **Ответственность:**
    - безопасное хранение access‑ и refresh‑токенов, полученных от внешних IdP;
    - шифрование токенов (например, с использованием KMS/HSM) и строгий контроль доступа;
    - ведение журнала доступа к токенам и попыток их использования.

#### 8. User Profile Service (Сервис пользовательских профилей)

- **Тип:** Container.
- **Ответственность:**
    - хранение профилей пользователей (PII + ссылки на медицинские данные и протезы) в пределах локальной юрисдикции;
    - хранение связи между внутренним user id BionicPRO, протезами и записями телеметрии в БД BionicPRO;
    - предоставление другим контейнерам (Core API) минимально необходимой информации о пользователе;
    - обеспечение того, чтобы пользователь имел доступ только к отчётам по своим протезам;
    - соблюдение требований локального законодательства о хранении персональных и медицинских данных (данные не покидают
      страну размещения).

#### 9. Apache Airflow (ETL-оркестратор)

- **Тип:** Container (Apache Airflow).
- **Ответственность:**
    - оркестрация ETL-процесса для подготовки витрины отчётности;
    - извлечение (Extract) данных с датчиков из BionicPRO DB (PostgreSQL) — телеметрия, миосигналы, статистика работы
      протеза;
    - извлечение (Extract) данных из CRM DB (Oracle Database 12) — информация о клиентах, заказах, производственных
      данных;
    - трансформация (Transform) — объединение данных из двух источников, очистка, агрегация, формирование структур
      витрины отчётности (например, объединение по user_id / prosthesis_id);
    - загрузка (Load) результатов в OLAP БД ClickHouse — формирование готовой витрины отчётности.
- **Взаимодействует с:**
    - BionicPRO DB (чтение данных с датчиков);
    - CRM DB (чтение данных о клиентах и заказах);
    - OLAP БД ClickHouse (запись сформированных витрин отчётности).

#### 10. OLAP БД (ClickHouse) — Витрина отчётности

- **Тип:** Container (ClickHouse).
- **Ответственность:**
    - хранение готовой витрины отчётности, сформированной ETL-процессом;
    - обеспечение быстрого аналитического чтения данных для формирования отчётов;
    - хранение агрегированных и объединённых данных с датчиков (из BionicPRO DB) и данных о клиентах/заказах (из CRM
      DB);
    - предоставление данных для Core API при запросе отчёта пользователем.
- **Взаимодействует с:**
    - Apache Airflow (получает данные от ETL-процесса — запись);
    - Core API BionicPRO (предоставляет данные для формирования отчётов — чтение).

#### 11. Локальный контур BionicPRO по странам (Regional Clusters)

Для каждой страны присутствия компании существует собственный набор контейнеров: Core API, BionicPRO DB, User Profile
Service, Identity Gateway, Encrypted Token Store, Apache Airflow, OLAP БД ClickHouse и локальные интеграции с внешними
IdP/каталогами, развёрнутый в дата‑центрах этой страны и подчиняющийся её законодательству.

## Внешние контейнеры и их связи

### 1. Интернет‑магазин (Web Shop, Bitrix24)

- **Тип:** Внешний Container.
- **Ответственность:** выбор протеза, оформление заказа и оплата.
- **Связи:**
    - Покупатель протеза → Интернет‑магазин: оформление заказа, оплата.
    - Интернет‑магазин → CRM: передача данных заказа.
    - Интернет‑магазин → Identity Gateway: запросы SSO/аутентификации пользователей.

### 2. CRM (Bitrix24 CRM) и CRM DB

- **Тип:** Внешние Containers (CRM, Oracle Database 12 или аналог).
- **Ответственность:**
    - хранение данных по заказам, клиентам и производственным процессам;
    - предоставление данных для ETL-процесса через CRM DB.
- **Связи:**
    - CRM ↔ CRM DB: операции записи и чтения данных о заказах и клиентах.
    - CRM DB → Apache Airflow: предоставление данных о заказах и пользователях для ETL-процесса (Extract).
    - CRM → Identity Gateway: SSO/аутентификация операторов и администраторов.

### 3. External IdP Systems (Keycloak, национальные IdP и др.)

- **Тип:** Внешние Containers.
- **Ответственность:** аутентификация пользователей по протоколам OAuth2/OIDC; выдача IdP‑access‑ и refresh‑токенов.
- **Связи:** Identity Gateway ↔ External IdP Systems: запросы /authorize, /token, /userinfo, introspection и т.п.

### 4. Local External Account Sources (по странам)

- **Тип:** Внешние Containers.
- **Ответственность:** хранение и управление учётными записями пользователей в конкретной стране.
- **Связи:** предоставление Identity Gateway данных о пользователях при аутентификации.

## Основные потоки данных (Data/Request Flows, Container Level)

### 1. Заказ протеза

- Покупатель протеза → Интернет‑магазин: выбор протеза, оформление заказа, оплата.
- Интернет‑магазин → CRM: передача информации о заказе; заказ доступен Оператору производства.

### 2. Эксплуатация протеза и донастройка

- Пилот протеза управляет протезом через миосигналы, считываемые Программой в чипе.
- Чип → Протез (актуаторы): физическое выполнение движений.
- Мобильное приложение ↔ Программа в чипе: отправка команд управления и получение статуса протеза.
- Мобильное приложение → Core API BionicPRO: отправка телеметрии и команд настройки.
- Программа в чипе → Core API BionicPRO: отправка телеметрии и технических данных через 4G‑модуль.
- Core API BionicPRO → BionicPRO DB: запись телеметрии, миосигналов и конфигураций.

### 3. ETL-процесс подготовки витрины отчётности

- Apache Airflow → BionicPRO DB (PostgreSQL): извлечение данных с датчиков — телеметрия протезов, миосигналы, статистика
  использования.
- Apache Airflow → CRM DB (Oracle Database 12): извлечение данных о клиентах, заказах, статусах производства.
- Apache Airflow выполняет трансформацию: объединение данных из двух источников по ключам (user_id, prosthesis_id),
  очистка, агрегация, формирование структур витрины.
- Apache Airflow → OLAP БД ClickHouse: загрузка готовой витрины отчётности.

### 4. Получение отчёта пользователем

- Пилот протеза → Мобильное приложение: запрос на получение отчёта о работе протеза.
- Мобильное приложение → Core API BionicPRO: HTTP-запрос на формирование/получение отчёта (с внутренним access-токеном
  BionicPRO).
- Core API → Identity Gateway: валидация внутреннего токена, получение user id.
- Core API → User Profile Service: проверка связи user id ↔ протезы, чтобы пользователь получил данные только по своим
  протезам.
- Core API → OLAP БД ClickHouse: чтение данных витрины отчётности по конкретному пользователю/протезу.
- Core API → Мобильное приложение: возврат готового отчёта (JSON/PDF) для скачивания пользователем.

### 5. ML‑анализ и улучшение моделей

- ML‑инженер → cli‑tool: запросы на выгрузку данных.
- cli‑tool → Core API / BionicPRO DB: чтение телеметрии и подготовка датасетов.
- ML‑инженер обновляет модели, которые затем используются в Программе в чипе.

### 6. Аутентификация и управление токенами

- Клиент (мобильное приложение, интернет‑магазин, CRM UI) → Identity Gateway: начало аутентификации (redirect/PKCE Code
  Flow).
- Identity Gateway → соответствующий External IdP / Local External Account Source: редирект пользователя и запрос
  токенов.
- External IdP → Identity Gateway: выдача IdP‑access‑ и refresh‑токенов.
- Identity Gateway → Encrypted Token Store: безопасное сохранение IdP‑токенов.
- Identity Gateway → Клиент: выдача внутренних access‑ и refresh‑токенов BionicPRO (прокси‑токены).
- Клиент → Core API / другие внутренние сервисы: запросы с внутренним access‑токеном BionicPRO.
- Внутренние сервисы → Identity Gateway: валидация внутренних токенов и получение информации о пользователе и его
  ролях.

### 7. Работа с пользовательскими профилями и медицинскими данными

- Identity Gateway ↔ User Profile Service: создание/поиск внутреннего пользователя на основе данных внешнего IdP;
  привязка нескольких внешних учётных записей к одному внутреннему user id.
- Core API → User Profile Service: получение минимальных данных профиля и связи user id ↔ протезы ↔ телеметрия.
- User Profile Service → локальные хранилища (BionicPRO DB и др.): доступ к персональным и медицинским данным только в
  пределах страны.
