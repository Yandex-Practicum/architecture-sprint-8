# Task 1

## Что сделал

В этом задании сделал две вещи:

1. Доработал исходную C4-диаграмму и показал, как можно безопаснее организовать работу с учетными данными пользователей.
2. Перевел текущее приложение на `Authorization Code + PKCE (S256)` в связке с Keycloak.

## Файлы

- `task1/BionicPRO_C4_model.drawio.xml` - доработанная диаграмма из задания
- `task1/BionicPRO_C4_model.original.drawio.xml` - исходная версия диаграммы до правок

## Что поменял в коде

- Во фронтенде включил `pkceMethod: "S256"` при инициализации `keycloak-js`.
- Добавил `silent-check-sso` страницу: `frontend/public/silent-check-sso.html`.
- Перед запросом к API добавил обновление токена через `keycloak.updateToken(30)`.
- В настройках клиента `reports-frontend` в Keycloak:
  - включил `standardFlowEnabled`;
  - отключил `implicitFlowEnabled`;
  - отключил `directAccessGrantsEnabled`;
  - включил `pkce.code.challenge.method = S256`;
  - сузил `redirectUris` до конкретных адресов приложения.

## Идея решения

Смысл решения такой:

- Пользователь входит не напрямую во все системы BionicPRO, а через единый контур аутентификации.
- Для этого на схему добавлен блок `Контур аутентификации / Keycloak`.
- Если компания работает в разных странах, можно подключать разные внешние системы входа. На схеме это блоки `Внешний IdP страны присутствия` и `Альтернативный внешний IdP`.
- Эти внешние системы нужны, чтобы подтверждать личность пользователя, но их токены не должны попадать в клиентское приложение.
- Само приложение должно работать уже с внутренним токеном BionicPRO.
- Чтобы не нарушать требования по хранению данных, персональные и медицинские данные остаются в локальном контуре. Для этого на схеме добавлен `Региональный каталог идентичностей`, где хранится только минимально необходимая информация для связки пользователя с системой.

## Изменения в диаграмме

Добавил:

- Контур аутентификации / Keycloak
- Региональный каталог идентичностей
- Внешний IdP страны присутствия
- Альтернативный внешний IdP

Также добавил связи:

- от `Интернет-магазин` к `Контур аутентификации / Keycloak`
- от `Приложение для донастройки протеза` к `Контур аутентификации / Keycloak`
- от `API` к `Контур аутентификации / Keycloak`
- от `Контур аутентификации / Keycloak` к внешним `IdP`
- от `Контур аутентификации / Keycloak` к `Региональный каталог идентичностей`
- от `Региональный каталог идентичностей` к `CRM DB`

## Почему это решение подходит

- Есть единая точка входа для пользователей.
- Можно подключать разные внешние системы входа для разных стран.
- Токены внешнего провайдера не уходят на фронтенд.
- Для браузерного клиента используется `PKCE`, что безопаснее обычного `Code Grant`.
- Персональные и медицинские данные не нужно выносить в общий контур.

## Как проверял

Проверка делалась локально через Docker:

- поднял проект через `docker compose up --build -d`
- открыл фронтенд на `http://localhost:3000`
- открыл Keycloak на `http://localhost:8080`
- выполнил вход через Keycloak
- в DevTools браузера проверил запрос на `/protocol/openid-connect/token`
- в этом запросе появился параметр `code_verifier`

Это подтверждает, что используется именно `Authorization Code + PKCE`.

Дополнительно можно проверить запрос на `/protocol/openid-connect/auth`. В нем должны быть `code_challenge` и `code_challenge_method=S256`.

## Важное замечание по запуску

При проверке выяснилось, что `keycloak` может стартовать раньше, чем PostgreSQL успевает принять соединения. Из-за этого при первом запуске контейнер `keycloak` у меня завершился с ошибкой подключения к БД.

Что важно:

- это не проблема PKCE и не ошибка в логике аутентификации
- зависимости запуска в `docker-compose.yaml` я отдельно не менял
- для локальной проверки хватило повторно запустить `keycloak`, когда база уже была готова
